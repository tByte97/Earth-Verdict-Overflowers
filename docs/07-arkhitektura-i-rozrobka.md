# 07 · Архітектура й порядок розробки

Стан на 14.11.2026. Основа: план у `05` (уже з урахуванням критики), дані з `03`, методика з
`04`. Усе нижче є пропозицією; рішення, які має ухвалити команда, зібрано в кінці.

## Чотири принципи, з яких випливає решта

1. **Кожне число на екрані повертає код.** LLM не пише ні нахилів, ні p, ні років, ні
   координат. Це забезпечується архітектурою (розділ «LLM»), а не лише промптом.
2. **Вердикт обчислюється детермінованою функцією.** LLM лише перетворює питання на справу і
   пояснює готовий результат словами.
3. **Справу видно й можна виправити до розрахунку.** Плашки картки: змінна, місце, сезон,
   період, напрямок твердження. Їх можна заповнити й без LLM.
4. **Демо не залежить від мережі.** Показові справи й ряди лежать файлами в репозиторії.

## Схема

```
 Браузер (React + MapLibre)                 Бекенд (FastAPI, Python)                 Зовнішні джерела
┌──────────────────────────────┐          ┌─────────────────────────────────┐
│ Глобус        │ Права панель │  /chat   │ chat: цикл LLM з інструментами  │──► Claude API (ключ на бекенді)
│ переліт,      │ чат          │ ◄──SSE──►│   find_place, run_check         │
│ точка,        │ картка справи│          │ check: ряд → сезон → статистика │──► NASA POWER (без ключа)
│ шар тренду    │ вердикт      │  /check  │   → стійкість → свідок → вердикт│──► NOAA NCEI Access (без ключа)
│               │ протокол     │ ◄───────►│ grid: сітка трендів + FDR       │──► Climate at a Glance (без ключа)
└──────────────────────────────┘  /grid   │ sources/: адаптери + кеш на диску│──► Giovanni API (токен Earthdata)
                                  /cases  │ cases/: закешовані показові      │──► Open-Meteo Geocoding (без ключа)
                                          └─────────────────────────────────┘
```

Фронтенд і бекенд в одному репозиторії; у продакшн-збірці FastAPI віддає статичний фронтенд,
тож це один сервіс з однією адресою.

## Потік одного питання

1. Користувач пише: «Чи стали літа в Києві спекотнішими?».
2. `/chat` передає повідомлення в LLM. Модель викликає `find_place("Київ")` і отримує
   кандидатів з `place_id` і координатами від геокодера.
3. Модель викликає `run_check` з `variable_id` з білого списку, `place_id`, сезоном, роками й
   напрямком твердження. Координат вона не передає, лише `place_id`.
4. Бекенд перевіряє аргументи (Pydantic), будує справу й одразу шле її у браузер подією
   `case`: панель показує плашки, глобус летить у точку.
5. Бекенд рахує перевірку (розділ «Розрахунок») і шле подію `result`: картка вердикту
   малюється з JSON, без участі LLM.
6. Той самий JSON іде в LLM як результат інструмента. Модель пише 2–4 речення пояснення.
   Охоронець чисел (розділ «LLM») перевіряє текст, і лише тоді він іде в браузер подією
   `explanation`.
7. Користувач міняє плашку → браузер викликає `/check` напряму, без LLM. Кнопка
   «Поясни ще раз» за бажанням.

## Бекенд

### Стек

Python 3.12, FastAPI, Pydantic v2, `httpx` (асинхронні запити), `numpy`, `scipy`,
`pymannkendall`, офіційний SDK `anthropic`. Оточення через `uv`. Тести `pytest`.

### Адаптери джерел

Кожен адаптер повертає один і той самий тип: місячний ряд із метаданими походження.

Кеш: файл JSON на запит у `data/cache/`, ім'я є хешем URL без токена. Показові справи
лежать окремо в `data/cases/` і комітяться в репозиторій. Для Giovanni кеш обов'язковий через
місячну квоту; поточну квоту читати з `GET /quota` і показувати в логах.

Для станції NOAA: брати найближчу в радіусі ~50 км з рядом не коротшим за обраний період і
пропусками не більше 10% місяців. Якщо такої немає, свідка немає, і картка це каже прямо.

### Розрахунок перевірки

```
місячний ряд → сезонний ряд (одне значення на рік) → статистика → стійкість
            → свідок (той самий конвеєр для станції) → вердикт → «скільки ще чекати»
```

- **Сезон:** `year` (12 місяців), `DJF`, `MAM`, `JJA`, `SON`, або один місяць. DJF року Y
  складається з грудня Y−1, січня й лютого Y. Температуру усереднюємо, опади сумуємо
  (у POWER `PRECTOTCORR` подано в мм/добу, тож множимо на кількість днів місяця). Рік із
  пропущеним місяцем сезону випадає.
- **Мінімум 15 років** у сезонному ряді. Коротший ряд дає «Не доведено: ряд закороткий» без
  тестів.
- **Методи** (`04`):
  - Манн–Кендалл із поправкою Хамеда–Рао (`pymannkendall.hamed_rao_modification_test`) і
    нахил Сена; 95% інтервал Сена рахуємо самі за рангами (формула з прототипу).
  - Регресія з t-тестом і поправкою Сантера на автокореляцію (ефективна кількість точок з
    r₁ залишків). Близько 30 рядків на `numpy`/`scipy`.
  - Звірка з прототипом: та сама функція на тих самих рядах має дати ті самі числа.
- **Тест стійкості до періоду:** обране вікно `[s, e]` плюс чотири варіанти `[s+3, e]`,
  `[s+6, e]`, `[s, e−3]`, `[s+3, e−3]`. Варіанти коротші за 15 років пропускаються. Результат:
  «значущий у k з n». Зсуви є стартовим вибором, підлаштувати після перших справ.
- **«Скільки ще чекати»** для «Не доведено»: формула Weatherhead (`04`) з поточних нахилу,
  розкиду й r₁.
- **Карта (`/grid`):** Манн–Кендалл і Сен у кожній клітинці сітки POWER, потім
  Бенджаміні–Хохберг на q = 0.05 по всіх клітинках вікна. Регіональне середнє зважувати на
  cos(широти).

### Вердикт

Чиста функція без мережі й LLM, повністю покрита тестами.

```
significant = mk.p < 0.05 і стійкість ≥ 4 з 5 з тим самим знаком нахилу
напрямок    = знак нахилу Сена

якщо ряд закороткий                      → Не доведено (закороткий ряд)
якщо не significant                      → Не доведено (+ скільки ще чекати)
якщо свідок значущий і знак протилежний  → Не доведено (джерела розходяться)
якщо напрямок збігається з твердженням   → Підтверджено
інакше                                   → Спростовано
```

Для твердження без напрямку («чи змінилось») значущий тренд дає «Підтверджено». Окремий
бейдж свідка: «два джерела згодні» / «підтверджено одним джерелом» / «станції поруч немає»
(таблиця в `05`, вектор 5).

### API бекенду

| Метод | Вхід | Вихід |
|---|---|---|
| `POST /api/chat` | `{messages, case?}` | потік SSE: `text`, `case`, `result`, `explanation`, `error` |
| `POST /api/check` | `CaseSpec` | `CheckResult` |
| `GET /api/grid` | `variable_id, season, start, end, bbox` | клітинки: `lat, lon, slope, p, q, significant` |
| `GET /api/variables` | — | білий список |
| `GET /api/places?q=` | — | кандидати геокодера (для ручного вводу) |
| `GET /api/cases`, `GET /api/cases/{id}` | — | закешовані показові справи (`CaseSpec` + `CheckResult` + сценарій автопрогравача) |

```python
class CaseSpec(BaseModel):
    claim_text: str
    variable_id: str              # лише з білого списку
    place: Place                  # place_id, name, lat, lon (із геокодера або кліку)
    season: Literal["year", "DJF", "MAM", "JJA", "SON"] | int   # int = номер місяця
    start_year: int
    end_year: int
    claim_direction: Literal["increase", "decrease", "change"]

class CheckResult(BaseModel):
    case: CaseSpec
    series: list[YearValue]       # сезонний ряд для графіка
    mk: MKResult                  # p, tau, z, поправка
    sen: SenResult                # slope за рік і за 10 років, ci_low, ci_high
    ols: OLSResult                # slope, p, r2, n_eff
    robustness: list[WindowResult]
    witness: WitnessResult | None # той самий набір для станції + відстань
    verdict: Literal["confirmed", "refuted", "not_proven"]
    reason: str                   # код причини: short_series, not_significant, sources_disagree, ...
    years_to_wait: float | None
    provenance: list[Provenance]  # для блоку «Як ми це перевірили»
```

## LLM

Рекомендація: Claude через офіційний SDK `anthropic`, модель `claude-opus-5-5`. Ключ лише в
змінній оточення бекенду.

- **Цикл із двома інструментами:** `find_place(query)` і `run_check(...)`. Обидва з
  `strict: true` і `additionalProperties: false`; `variable_id` і `season` є `enum`, тож
  модель фізично не може вибрати змінну поза білим списком. `tool_choice` лишається `auto`
  (примусовий вибір інструмента ця модель не приймає), а потрібну поведінку задає системний
  промпт.
- **Білий список у системному промпті**, а не окремим інструментом: він короткий і
  незмінний, тож добре кешується (`cache_control`).
- **`output_config.effort: "low"`** для чату (у цієї моделі за замовчуванням `medium`);
  підняти, якщо модель погано розбирає питання. Потокова відповідь, щоб текст ішов у SSE.
- **Запасна модель при відмові:** `fallbacks: "default"` з бета-заголовком
  `server-side-fallback-2026-07-01`; завжди перевіряти `stop_reason` перед читанням відповіді.
- **Охоронець чисел.** Після генерації пояснення витягти всі числа з тексту регулярним
  виразом. Кожне має збігтися (з урахуванням округлення) з числом із `CheckResult` або
  `CaseSpec`. Якщо ні, один повтор із вказівкою на зайве число; якщо знову ні, замість
  пояснення шаблонний текст із коду. Картка вердикту від цього не залежить: її числа
  малюються з JSON.
- **Таймаут і відмова LLM:** панель показує повідомлення й пропонує заповнити плашки вручну.

Якщо команда вже має ключ іншого провайдера, архітектура не змінюється: міняється лише
`app/llm/`.

## Фронтенд

Vite + React + TypeScript, MapLibre GL JS 5 (проєкція globe), Chart.js для графіка зі смугою
інтервалу.

- **Глобус:** `flyTo` до точки справи; маркер точки й станції; для етапу 5 шар клітинок
  тренду (значущі після FDR яскраві, решта бліді); для пари регіонів два контури й лінія.
- **Права панель**, зверху вниз: чат → картка справи (плашки, кожна з випадним списком) →
  вердикт (стан, швидкість за 10 років, p, інтервал, бейдж свідка, стійкість «k з n») →
  графік (ряд, лінія Сена, смуга інтервалу, ряд станції поруч) → розгортний блок «Як ми це
  перевірили» (три методи, вікна стійкості, походження кожного числа, правила зі Statsig).
- **Стан справи в URL** (`#case=...`), як у прототипі: посилання на будь-яку перевірку.
- **Автопрогравач показових справ:** друкує питання, викликає `/api/cases/{id}`, програє
  події тим самим кодом, що й живий `/chat`.

## Тести

- `stats/`: синтетичні ряди з відомим нахилом і шумом; ряд з одним викидом (Сен стійкий,
  регресія ні); ряд з автокореляцією (поправка зменшує значущість).
- Звірка з прототипом на 2–3 рядах POWER: ті самі нахил і p.
- Звірка з NOAA: нахил глобального ряду Climate at a Glance за 1901–2000 і за останні
  десятиліття має бути близьким до опублікованого NOAA тренду.
- `verdict.py`: таблиця всіх гілок.
- `guard.py`: текст із чужим числом відхиляється, з округленим своїм проходить.
- Адаптери: на збережених відповідях з `data/cache`, без мережі.

## Розгортання

Один сервіс: бекенд з вбудованою статикою фронтенду, контейнер на будь-якому безкоштовному
хостингу (Render, Fly.io, Railway). Секрети: `ANTHROPIC_API_KEY`, `EARTHDATA_TOKEN`. Для
відео й журі показові справи працюють і без зовнішніх API. Запасний варіант: локальний запуск
і запис відео.

## Порядок розробки

Нарізка тонкими шарами: після кожного кроку є робочий продукт від питання до відповіді.
Години є прикидками. «Б» — бекенд, «Ф» — фронтенд.

| Крок | Що | Хто | Год | Готово, коли |
|---|---|---|---|---|
| 0 | Скелет: `backend/` з `/health`, `frontend/` з глобусом, `uv`, Vite, `.gitignore` | Б+Ф | 1 | Обидва запускаються однією командою кожен |
| 1 | `power.py`, `seasonal.py`, `trend.py`, `verdict.py` + тести; `POST /api/check` | Б | 3–4 | `curl` на Київ, JJA, 1981–2025 повертає вердикт |
